## 1. Mission

Continuously discover, evaluate, select, acquire, adapt, integrate, test,
document, and maintain the best available free and open-source components for
this project — **without ever making the existing project subordinate to an
external repository**.

The objective is not to collect repositories. It is to turn the strongest
reusable components into a coherent, secure, maintainable production system.

## 2. Absolute priorities (in order)

1. **The existing project is the source of truth.** Never rebuild because a
   GitHub repo looks similar; never replace working functionality without
   evidence; never import an entire application to obtain one algorithm.
2. **License before code.** No copying before license verification; unclear
   license ⇒ `LICENSE_UNVERIFIED` ⇒ rejected for production.
3. **Reuse before import.** If existing code (or the standard library) covers
   the need, no new dependency is added (`docs/dependency-decisions.md` is the
   ratified example of this policy in action — a whole wishlist manifest was
   rejected and replaced with internal implementations).
4. **Adapters at the boundary.** External engines enter behind provider
   interfaces (`LLMProvider`, `EmbeddingProvider`, `RerankerProvider`,
   `OCRProvider`, retriever abstraction) — never into the domain layer.
5. **Egyptian legal domain stays in-house.** External projects provide
   *technology*; they never become the authority over legal interpretation,
   and legal *datasets* are not knowledge until they pass source verification
   + human review.

## 3. Integration lifecycle

```
DISCOVER → FILTER → LICENSE CHECK → MAINTENANCE CHECK → ARCHITECTURE CHECK
→ SECURITY CHECK → DEPENDENCY CHECK → CODE QUALITY CHECK → FUNCTIONALITY CHECK
→ LEGAL/DOMAIN RELEVANCE CHECK → COMPARE ALTERNATIVES → SELECT → ISOLATE
→ ADAPT → INTEGRATE → TEST → DOCUMENT → MONITOR → UPDATE
```

Stage failure at any point stops the process (record it in
`docs/OSS_DECISIONS.md` and move on).

## 7. Security posture (summary)

Detailed: [`OSS_SECURITY.md`](OSS_SECURITY.md).

- CI: bandit (SAST) on `local-ai/services`, flake8-bandit rules.
- This repo: registry gate + SBOM generation (extendable to audit/SAST steps).
- Browser-exposed keys are accepted only for demo-grade hosted features and
  must degrade to on-device engines (documented per module).
- No floating refs; direct deps pinned; git/file specs rejected by lint.

## 8. Intake process (new component)

1. **Search the project first** (§21 duplicate detection) — if existing code
   suffices, stop here and record the rejection.
2. Fill a **Candidate Record** (§16 fields) in `docs/OSS_DECISIONS.md`.
3. License gate → SPDX + compatibility with our distribution model (web SPA +
   self-hosted services + mobile). Unclear ⇒ reject.
4. Security inspection (§17 checklist; §18 red flags are auto-reject).
5. For TYPE D/E/G: build in `sandbox/oss/<name>/` first; only the surviving
   extract gets integrated, with provenance (§9).
6. Register in `config/oss_registry.yaml` (+ `default_licenses` for trivial
   MIT-tail packages).
7. `node scripts/oss-registry-lint.mjs` must pass; add tests if TYPE A/B/J.
8. Regenerate SBOM; update this document.
9. Set an explicit `update_policy` (default `SECURITY_ONLY`).

## 10. Update & monitoring

- Policies per component in the YAML; default `SECURITY_ONLY`.
- Security advisories override cycles: flag `SECURITY_UPDATE_REQUIRED`,
  evaluate → patch → test → deploy → document.
- Scheduled audit: `.github/workflows/oss-audit.yml` (weekly registry lint +
  SBOM regeneration + SBOM drift check + review-staleness report + advisory
  `npm audit`).
- `candidates:` list in the YAML tracks open evaluations; `rejected:` prevents
  re-proposal churn (full reasoning in DECISIONS).

## 11. Enforcement machinery

Everything above is backed by executable checks — the policy is not prose-only:

| Check | Command | Gate behavior |
|-------|---------|--------------|
| Registry lint ("no mystery dependencies") | `bun run oss:lint` → `node scripts/oss-registry-lint.mjs` | exit 1 on: unregistered direct deps (npm, local-ai frontend, Python pins, pub, Gradle), floating git/`latest` refs, banned packages, `LICENSE_UNVERIFIED` in production surfaces |
| SBOM (CycloneDX 1.5) | `bun run oss:sbom` → `node scripts/generate-sbom.mjs` | regenerates `sbom/cyclonedx.json`; zero-dep; CI fails on drift vs the committed SBOM when manifests change |
| Combined audit | `bun run oss:audit` | lint + SBOM in one step |
| CI schedule | `.github/workflows/oss-audit.yml` | weekly + on manifest/registry PRs; staleness report flags components unreviewed > 180 days |

**SBOM license enrichment policy** (current ratio: **192/197 components**).
Licenses are attached from, in order: registry `components` records →
`default_licenses` (incl. scoped wildcards like `@capacitor/*`) →
`license_pypi` facts → `artifact_alias` mappings (registry key ≠ maven
artifact name) → `license_group_policy` group-prefix facts (androidx.*/
kotlin/etc., each with its evidence note in the YAML). Non-SPDX strings
(e.g. "Google ML Kit Terms (on-device, free)") are emitted as named licenses,
never as SPDX ids. The five unenriched components are this repo's own
first-party images (`crimsys/*`) — deliberately not third-party OSS.
